## Целевое поведение системы

Пользователь вводит любой запрос в чат → система параллельно делает два поиска:
1. Метапоиск по БД (название, автор, ключевые слова, абстракт)
2. Семантический поиск по тексту PDF через Qdrant

Результаты объединяются в единый список, отсортированный по релевантности. В чате для каждой публикации показывается откуда она нашлась и фрагменты текста PDF с номерами страниц (если нашлась через RAG). LLM-планировщик (Ollama) убирается полностью — на CPU он слишком медленный и не нужен.

## Изменение 1 — Убрать LLM планировщик, упростить backend-ai

### Файлы
`backend-ai/app/services/search_planner.py`, `backend-ai/app/services/llm_planner.py`, `backend-ai/app/services/rag_search.py`

### Что сделать

Удалить `llm_planner.py` и всё что с ним связано. Rule-based планировщик остаётся как единственный — он уже хорошо справляется.

В `build_rag_search` убрать проверку на `semantic.scope` как условие запуска RAG — теперь RAG запускается всегда для любого поискового запроса. Убрать fallback на `message` в `_build_retrieval_query`:

```python
def _build_retrieval_query(message, plan, filters) -> str | None:
    candidates = [
        plan.semantic.query,
        filters.pdf_text_query,
        filters.text_query,
        filters.refine_text_query,
        filters.title,
        " ".join(filters.keyword),
        # message убрать отсюда
    ]
    for candidate in candidates:
        if candidate and candidate.strip():
            return candidate.strip()
    return None
```

## Изменение 2 — Объединение результатов в основном бэкенде

### Файлы
`backend/app/services/articles/public.py`, `backend/app/routers/articles.py`

### Что сделать

Добавить в `list_articles` параметр `rag_article_ids: list[int] | None` — упорядоченный список article_id из RAG (от наиболее к наименее релевантному).

Логика объединения:

```python
# Публикации делятся на три группы:
# 1. Найдены и в метапоиске и в RAG → самый высокий приоритет
# 2. Найдены только в RAG → средний приоритет  
# 3. Найдены только в метапоиске → обычный порядок

# При sort_by="relevance" и наличии rag_article_ids:
# ORDER BY:
#   - сначала те что есть в rag_article_ids (в порядке RAG score)
#   - потом остальные по relevance_score из метапоиска
```

Реализация через `FIELD()` в SQL или двухэтапная: сначала получить id из обоих источников, потом объединить в Python и запросить данные.

Добавить в ответ `ArticleListItem` поле `rag_matches` — список фрагментов PDF для этой публикации (если нашлась через RAG):

## Изменение 3 — Новый эндпоинт поиска с RAG

### Файлы
`backend-ai/app/routers/publications.py` или новый роутер в `backend`

### Что сделать

Добавить эндпоинт который делает оба поиска и возвращает объединённый результат. Два варианта архитектуры:

**Вариант A — оркестрация в backend-ai:**
`backend-ai` вызывает Qdrant, формирует `rag_article_ids` и `rag_matches`, затем вызывает `backend` передавая их как параметры. Фронтенд обращается только к `backend-ai`.

**Вариант B — оркестрация на фронтенде:**
Фронтенд параллельно вызывает `backend-ai` (за RAG-результатами) и `backend` (за публикациями), объединяет на клиенте.

Рекомендуется **вариант A** — меньше запросов, логика объединения на сервере, фронтенд получает готовый результат.
